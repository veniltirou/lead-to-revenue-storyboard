The One-Off — An OIC Replenishment Integration for a Single Hilltop Site

A follow-up in the OIC series. Earlier chapters covered a real-time sales order integration from a non-Oracle customer into ABC's Order Management. This one tackles a different shape of problem — a genuine one-off. A single remote hilltop office site of Home, Sweet Home needs its restock route driver to place replenishment orders, from a non-Oracle mobile app, into ABC Corporation's Oracle Fusion Cloud Procurement. Rather than reconfigure the core system for one edge case, Harrison builds a targeted OIC integration around Oracle's own externally-managed-requisition pattern — narrated phase by phase, with the real Procurement field names and a full fault-handling path.

Business Scenario: Most of ABC's replenishment runs through its standard Oracle ecosystem. But one HSH property — a remote hilltop office with only a handful of occupants and a special route-driver arrangement — falls outside the normal flow. Its route driver needs to log low-stock items on-site and have a purchase requisition created automatically in Oracle Procurement. James brings this one-off to Harrison; Harrison first checks whether Oracle's own Procurement can accept requisitions originating from a non-Oracle system, discovers Oracle's externally-managed-requisition pattern, and builds an OIC integration around it. This chapter walks all five phases — and, importantly, what happens when the requisition fails.
A note on technical accuracy: The field names, REST resource path, and submit mechanism in this chapter (ExternallyManagedFlag, PreparerEmail, RequesterEmail, LineTypeCode: "Goods", DestinationType: "Expense", UOM: "Each", the distributions child array, purchaseRequisitions, and the submitRequisition action) are checked against Oracle's current documentation for Oracle Fusion Cloud Procurement, including Oracle's own worked example for creating externally-managed requisitions. The integration user requires the Procurement REST Service Duty role (ORA_PO_PROCUREMENT_REST_SERVICE_DUTY). The diagrams are illustrative reconstructions built to be technically accurate, not actual product screenshots — Oracle's UI and API details can change across releases.

1The Ask

What this shows: James brings Harrison a one-off — a single remote HSH hilltop site needs its restock route driver to place replenishment orders, from a non-Oracle mobile app, into ABC's Oracle Procurement. It's a scenario the standard setup doesn't cover.

2The Situation

What this shows: The real-world scenario, wordless — a route driver restocking beverages at a remote hilltop office site. Few occupants, a special route arrangement, off the beaten path: exactly the kind of edge case that justifies a targeted integration rather than reconfiguring the core system.

3Harrison Takes It On

What this shows: Rather than build from scratch, Harrison first checks whether Oracle's own Procurement can accept requisitions from a non-Oracle system — and finds Oracle's externally-managed-requisition pattern, purpose-built for exactly this. He spends the week implementing it in OIC.

4The Overview

What this shows: A week later, Harrison presents the finished design — the complete five-phase replenishment flow in one diagram. The route driver's app POSTs to ABC's own trigger at the top; from there the flow runs left to right through to the requisition created and submitted in Oracle, with the fault-handling path drawn in.

5Phase 1 — Secure OAuth 2.0 Connection

What this shows: Before the route driver's app can call ABC at all, it proves its identity — a token request (grant_type=client_credentials), OCI IAM validating the client and issuing a JWT bearer token (commonly ~3600s), then presenting Authorization: Bearer <TOKEN> on the call to ABC's own endpoint. The app only ever knows ABC's URI, never Oracle Procurement.

6Phase 2 — Inbound Trigger & Logging

What this shows: The route driver's simple visit payload — visit ID, driver ID, site and machine IDs, and the low-stock items — arrives at ABC's REST trigger, /logReplenishmentVisit, and a Logger records it to the Activity Stream immediately, before any processing.

7Phase 3 — Enrichment (Lookup + Assign)

What this shows: A Lookup resolves the driver's siteId, machineId, and sku into Oracle's item and the hilltop site's DeliverToLocationCode. An Assign sets the fixed values the app never sends — RequisitioningBU, LineTypeCode: "Goods", DestinationType: "Expense", and ExternallyManagedFlag: true.

8Phase 4a — The Happy Path (Create + Submit)

What this shows: Inside a Scope, two separate Invokes. First a POST to Oracle's real purchaseRequisitions resource creates the requisition in Incomplete status; then a second call submits it via the submitRequisition action — and because it's externally managed, Oracle bypasses the approval workflow. Note the two-call reality: "created" and "submitted" are distinct steps, and the gap between them is a real failure surface.

9Phase 4b — When It Fails (The Fault Handler)

What this shows: The error path, in its own spotlight. If either invoke fails — including the real "created but not submitted" gap — the Scope Fault Handler fires: a Logger captures the fault, an ATP Adapter INSERTs the failure (transaction ID, error code, timestamp, full failed payload, and which step failed) into a REPLENISHMENT_ERROR_LOG table, an [URGENT] email alerts ABC's Procurement contact, and a Rethrow pushes the failure onto OIC's Errors page so it stays visible and resubmittable. A Global Fault Handler sits beneath as the last-resort net.

10Phase 5 — Simplified Response

What this shows: On success, a second Mapper narrows Oracle's full response down to just what the route driver's app needs — status, requisition number, and a plain-language message — and Respond returns it. Simple in, simple out.

11The Whole Flow, and Why a One-Off Deserves OIC

What this shows: The complete flow once more, end to end. The takeaway: the vast majority of ABC's replenishment runs through the standard Oracle ecosystem — but a genuine one-off like this hilltop site is exactly where a lightweight, targeted OIC integration earns its place, without disturbing the core system.

Why This Chapter Matters

The takeaway: The real architectural decision here isn't any single action — it's knowing when to reach for an integration at all. The vast majority of ABC's replenishment flows through the standard Oracle ecosystem, and that's correct. A genuine one-off — a remote hilltop site with a handful of occupants and a special route-driver arrangement — is exactly the case where a lightweight, targeted OIC integration earns its place, rather than bending the core system around a single edge case. And rather than reinventing anything, Harrison used Oracle's own externally-managed-requisition pattern — the create-then-submit sequence Oracle documents for exactly this "outside system creates the requisition" scenario. The two-call gap between create and submit is a real failure surface, which is precisely why the scope fault handler, the ATP error log, the URGENT alert, and the rethrow all exist: so a failure is captured, announced, and recoverable rather than silently lost.
